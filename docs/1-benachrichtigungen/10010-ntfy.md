# ntfy — Self-hosted Push-Notifications mit iOS-Support

ntfy ist ein einfacher, selbst gehosteter Pub/Sub-Notification-Dienst. Im Gegensatz zu Gotify unterstützt ntfy **echte iOS-Push-Nachrichten** über Apple Push Notification Service (APNs), indem es Nachrichten über das ntfy.sh-Relay weiterleitet.

---

## Warum ntfy statt Gotify für iOS?

|             | Gotify                              | ntfy                        |
|-------------|-------------------------------------|-----------------------------|
| Android     | ✓ nativ                             | ✓ nativ                     |
| iOS         | ✗ (WebSocket, kein Background-Push) | ✓ (APNs via upstream-Relay) |
| Self-hosted | ✓                                   | ✓                           |
| Auth        | ✓                                   | ✓ (optional)                |
| HTTP-API    | ✓                                   | ✓                           |

**Empfehlung:** Gotify für interne Logs/Android behalten; ntfy für iOS-Benachrichtigungen nutzen.

---

## Architektur

```
Alertmanager / beliebiger curl-Sender
        │
        ▼
ntfy-Server (https://ntfy-tech.pke-lab.de / https://ntfy.tech.homeserver)
        │
        ├── Android-App (direkt via WebSocket)
        │
        └── ntfy.sh-Relay ──► Apple APNs ──► iOS-App
```

Das `upstream-base-url: https://ntfy.sh` in der Konfiguration aktiviert diesen Relay. Die Nachrichteninhalte verlassen dabei deinen Server im Klartext in Richtung ntfy.sh — für sensible Daten ggf. End-to-End-Verschlüsselung aktivieren (siehe unten).

## Deployment

ArgoCD deployt ntfy automatisch sobald der Branch auf `main` gemergt ist:

```
argocd/apps/platform/ntfy/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── configmap.yaml      # server.yml
    ├── deployment.yaml
    ├── ingress.yaml
    ├── pvc.yaml
    ├── service.yaml
    └── serviceaccount.yaml
```

URL nach dem Deployment (Domain-Tier `tech`, siehe
[docs/c-netzwerk-dns/c0040-domain-tiers.md](../c-netzwerk-dns/c0040-domain-tiers.md)):
- Intern (LAN/Tailscale): **https://ntfy.tech.homeserver**
- Extern (Cloudflare-Tunnel): **https://ntfy-tech.pke-lab.de**

## `base-url` — Pflicht für iOS-Push-Inhalte

`config.base-url` (in `argocd/apps/platform/ntfy/values.yaml`) muss auf den
**extern erreichbaren HTTPS-Host** (`https://ntfy-tech.pke-lab.de`) zeigen,
nicht auf den internen `.tech.homeserver`-Host.

Grund: ntfy.sh liefert dem iPhone per APNs nur einen stillen "Wach
auf"-Push. Der eigentliche Nachrichteninhalt wird danach von der
Notification-Service-Extension der App per GET gegen `${base-url}/...`
nachgeladen — und zwar auf dem Netz, in dem sich das Handy gerade
befindet (Mobilfunk, fremdes WLAN, ...), nicht zwingend im Heimnetz.

Zeigt `base-url` auf einen LAN-only-Hostnamen oder auf `http://` statt
`https://`, schlägt dieser Nachlade-Request außerhalb des Heimnetzes fehl
(DNS unauflösbar bzw. von iOS' App Transport Security blockiert) — die
Push-Benachrichtigung kommt zwar an (Sperrbildschirm zeigt einen
Platzhalter), aber ohne Inhalt, und die Nachricht taucht auch beim
Öffnen der App nicht auf. Passiert am 2026-09-15 real: `base-url` stand
auf `http://ntfy.tech.homeserver`, obwohl `ntfy-tech.pke-lab.de` als
öffentlicher Host bereits existierte.

## iOS einrichten

1. **ntfy-App** aus dem [App Store](https://apps.apple.com/app/ntfy/id1625396347) installieren
2. App öffnen → **+** → Server-URL eintragen: `https://ntfy-tech.pke-lab.de`
3. Topic abonnieren, z.B. `Home-Lab`
4. Benachrichtigungen in den iOS-Einstellungen für ntfy erlauben

> **Hinweis:** Das Topic ist öffentlich zugänglich solange `auth-default-access: read-write` gesetzt ist. Für private Topics Auth aktivieren (siehe unten).

## Nachrichten senden

### Einfachste Form
```bash
curl -d "Hallo Welt" https://ntfy-tech.pke-lab.de/Home-Lab
```

### Mit Titel und Priorität
```bash
curl \
  -H "Title: Home-Server Alert" \
  -H "Priority: high" \
  -H "Tags: warning" \
  -d "Festplatte > 90% voll" \
  https://ntfy-tech.pke-lab.de/Home-Lab
```

### Prioritäten
| Wert             | Bedeutung                    |
|------------------|------------------------------|
| `min` / `1`      | Stumm                        |
| `low` / `2`      | Leise                        |
| `default` / `3`  | Normal                       |
| `high` / `4`     | Laut                         |
| `urgent` / `5`   | Dringend, DND wird ignoriert |

### Tags (Emoji-Icons in der App)
```bash
-H "Tags: white_check_mark"   # 
-H "Tags: warning"             # 
-H "Tags: rotating_light"      # 
```

Vollständige Emoji-Liste: https://docs.ntfy.sh/emojis/

## DNS

Kein manueller dnsmasq-Eintrag nötig: dnsmasq (`address=/homeserver/<ip>`)
und der CoreDNS-Forward im Cluster matchen bereits die komplette
`homeserver`-Zone inkl. aller Subdomains, `ntfy.tech.homeserver` löst also
automatisch mit auf, siehe
[docs/c-netzwerk-dns/c0040-domain-tiers.md](../c-netzwerk-dns/c0040-domain-tiers.md).
Der externe Host `ntfy-tech.pke-lab.de` läuft über die
Cloudflare-Tunnel-Wildcard-Regel für `*.pke-lab.de` — ebenfalls kein
App-spezifischer DNS-Eintrag nötig.

## Authentifizierung aktivieren (optional)

Wenn Topics nicht öffentlich sein sollen, in `values.yaml` ändern:

```yaml
config:
  auth-default-access: "deny-all"
```

Dann User anlegen (SSH auf den Server, kubectl exec):

```bash
kubectl -n ntfy exec -it deploy/ntfy -- ntfy user add --role=admin admin
kubectl -n ntfy exec -it deploy/ntfy -- ntfy user add publisher
kubectl -n ntfy exec -it deploy/ntfy -- ntfy access publisher Home-Lab rw
```

Nachrichten dann mit Basic Auth senden:

```bash
curl -u publisher:PASSWORT -d "Test" https://ntfy-tech.pke-lab.de/Home-Lab
```

---

## End-to-End-Verschlüsselung (optional)

Wenn Nachrichten über ntfy.sh-Relay nicht im Klartext weitergeleitet werden sollen:

```bash
# Lokal verschlüsseln (ntfy CLI)
ntfy publish --password "geheim" https://ntfy-tech.pke-lab.de/Home-Lab "Meine Nachricht"
```

In der iOS-App: Topic-Einstellungen → Passwort eintragen.

## Troubleshooting

### Pod startet nicht
```bash
kubectl -n ntfy get pods
kubectl -n ntfy logs deploy/ntfy
```

### Push kommt an, aber ohne Inhalt / nichts in der App (obwohl Server aktiv publiziert)
Das ist praktisch immer ein falsches `base-url`, siehe
[`base-url` — Pflicht für iOS-Push-Inhalte](#base-url--pflicht-für-ios-push-inhalte)
oben. Prüfen:
```bash
kubectl -n ntfy get configmap ntfy-config -o jsonpath='{.data.server\.yml}'
```
Muss `base-url: "https://ntfy-tech.pke-lab.de"` enthalten — jede andere URL
(intern, http://) bricht das Nachladen der Nachricht durch die iOS-App.
Nach einer Korrektur: `kubectl -n ntfy rollout restart deploy/ntfy`.

Ob tatsächlich publiziert wird, zeigen die Server-Stats im Log
(`messages_published`, `messages_cached`):
```bash
kubectl -n ntfy logs deploy/ntfy --tail=5
```

### iOS-Benachrichtigungen kommen gar nicht an
1. Prüfen ob `upstream-base-url: https://ntfy.sh` in der ConfigMap gesetzt ist:
   ```bash
   kubectl -n ntfy get configmap ntfy-config -o yaml
   ```
2. Prüfen ob der Pod Internetzugang hat (ntfy.sh muss erreichbar sein):
   ```bash
   kubectl -n ntfy exec deploy/ntfy -- wget -q -O- https://ntfy.sh/v1/health
   ```
3. iOS-Benachrichtigungen in Einstellungen → ntfy → Mitteilungen prüfen

### Nachrichten testen
```bash
# Direkt vom Cluster aus
kubectl -n ntfy exec deploy/ntfy -- \
  wget -q -O- --post-data="Test von kubectl" http://localhost:8080/test
```
