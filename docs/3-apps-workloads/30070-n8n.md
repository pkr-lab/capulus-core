# n8n — Low-Code-Automatisierung

n8n ist ein selbst gehosteter Workflow-Automatisierer (Open-Source-Alternative
zu Zapier/Make). Über eine visuelle Oberfläche lassen sich Dienste verknüpfen,
z. B.:

- Neues Dokument in Paperless → ntfy-Push
- Neuer GitHub-Release → Zammad-Ticket
- Wetterwarnung DWD → ntfy-Alert
- Neues Ticket in externem Zammad → KI-Antwortentwurf (täglich, lokales LLM)
- Neue Mail von einer bestimmten Adresse → Nachricht in einen WhatsApp-Kanal

---

## Architektur

```
n8n.prod.homeserver  →  Traefik  →  n8n (Port 5678)
                                   └── PVC: data (5 Gi, nas)
```

- **Datenbank:** SQLite (in `/home/node/.n8n`)
- **Webhooks:** erreichbar unter `http://n8n.prod.homeserver/webhook/...`

---

## Erster Start

n8n ist nach dem Deploy unter **http://n8n.prod.homeserver** erreichbar. Beim
ersten Öffnen wird ein Owner-Account angelegt.

## Beispiel-Workflow: Paperless → ntfy

```
Trigger: Paperless Webhook (POST /webhook/paperless)
  → HTTP Request: GET paperless.homeserver/api/documents/{id}/
  → ntfy Node: Push "📄 Neues Dokument: {title}"
```

1. In n8n: *Neuer Workflow* → Trigger: **Webhook**
2. Webhook-URL aus n8n kopieren
3. In Paperless: *Einstellungen* → *Workflow-Trigger* → URL eintragen
4. ntfy-Node hinzufügen, Topic und Server konfigurieren

## Beispiel-Workflow: Externer Zammad → KI-Antwortentwurf (Ollama)

Zwei zusammengehörige, importierbare Workflows unter
`argocd/apps/tech/n8n/workflows/` — aufgeteilt, damit die
Lebenszyklus-Steuerung des lokalen LLM (Start/Stop) sauber von der
eigentlichen Ticket-Verarbeitung getrennt ist:

### A) `zammad-externer-ki-lauf-taeglich.json` (Haupt-Workflow)

**Schedule Trigger** (**1× täglich**, Default 07:00 Uhr) orchestriert den
kompletten Lebenszyklus des lokalen LLM
([Ollama](300g0-ollama.md), läuft mit `replicas: 0` im Ruhezustand — kein
Dauerbetrieb):
1. **Worker-0 wecken** — `POST carplay-api.prod.homeserver/api/power/wake`
   (`{"target": "worker-0"}`), da der bestehende `cluster_power_manager`
   nur reaktiv auf Last reagiert, nicht auf diesen konkreten Bedarf.
2. **Ollama hochskalieren** — direkter Kubernetes-API-Call (PATCH auf die
   Scale-Subresource) auf `replicas: 1`, authentifiziert mit dem
   automatisch gemounteten ServiceAccount-Token des n8n-Pods selbst (RBAC
   dafür in `argocd/apps/tech/ollama/templates/role-n8n-scaler.yaml`
   — n8n darf NUR dieses eine Deployment skalieren).
3. **Wait** (Startwert 150s) für Node-Boot + Pod-Start + Ollama-Bereitschaft.
4. **Execute Workflow** ruft Sub-Workflow B auf und wartet auf dessen
   Abschluss.
5. **Ollama herunterskalieren** — dieselbe PATCH-Logik, zurück auf
   `replicas: 0`. Läuft garantiert, auch wenn Sub-Workflow B an dem Tag 0
   Tickets gefunden hat (siehe unten).

Details zum Scale-to-Zero-Pattern, RBAC und ArgoCD-`ignoreDifferences`:
**[300g0-ollama.md](300g0-ollama.md)**.

### B) `zammad-tickets-verarbeiten.json` (Sub-Workflow)

Kein eigener Zeitplan — startet ausschließlich per **Execute Workflow
Trigger**, aufgerufen von Workflow A, während Ollama bereits läuft. Nutzt
für alle drei direkten Zammad-Schritte den **nativen
`n8n-nodes-base.zammad`-Node**, dessen Ticket-Ressource *nur* die
Operationen `create`/`get`/`getAll`/`update`/`delete` kennt — es gibt
**keine eigene „Ticket Article“-Ressource** und `getAll` akzeptiert
**keinerlei Filter-/Query-Parameter** (ruft serverseitig ungefiltert
`GET /tickets` auf der externen Zammad-Instanz `https://ticket.emue365.de`
auf, anderer Account als `zammad.homeserver`); zurückgegebene Ticket-Felder
sind zudem rohe IDs (`state_id`/`owner_id`/`group_id`), keine Namen. Der
Workflow filtert deshalb clientseitig **nach** dem Get-Many-Node im
IF-Node „Nur relevante Tickets“ auf `state_id` (Status „new“ ODER „open“,
per Boolean-Expression `[1, 2].includes($json.state_id)` — ein einzelnes
Filter-Feld bietet kein „IN (...)“ an) und `owner_id` (= zugewiesener
KI-Agent, Vergleich **numerisch**, nicht als String — dazu gleich mehr) —
**nur Tickets, deren `owner_id` mit dem eingetragenen Wert übereinstimmt
UND die nicht bereits geschlossen sind, werden bearbeitet**, keine
anderen. Beim ersten echten Testlauf (27.08.2026) zeigte sich außerdem:
der IF-Node verglich `owner_id` ursprünglich als **String** gegen das
tatsächlich numerische Zammad-Feld — unbemerkt, solange der Node mit
`typeValidation: loose` lief, aber sobald n8n ihn beim Öffnen/Speichern in
der UI automatisch auf das neuere Schema (`v2.2`, `typeValidation:
strict`) hochzieht, bricht der Vergleich hart mit `Wrong type` ab, sobald
ein Ticket mit numerischem `owner_id` durchläuft. Bei eigenen Anpassungen
an diesem IF-Node also auf numerische Operatoren/Werte für numerische
Zammad-Felder achten, nicht auf Strings. Der Node
„Ticket-Artikel laden“ ist `Ticket: Get` (Feld `id`) — die Zammad-API
liefert dabei automatisch ein `articles`-Array mit dem Verlauf mit (der
native Node ruft dafür intern zusätzlich `/ticket_articles/by_ticket/:id`
auf), eine separate „Get Many“-Artikelabfrage ist nicht nötig. Der
Artikel-Verlauf geht per HTTP-Request an das lokale Ollama
(`http://ollama.ollama.svc.cluster.local:11434/api/generate`, Modell
`llama3.2:3b` — ursprünglich `llama3.1:8b` geplant, siehe
[300g0-ollama.md](300g0-ollama.md) für den Grund der Umstellung —, kein
Auth nötig). Gespeichert wird per `Ticket: Update`
(Feld `id`, **kein** `article`-Feld — das gibt es nur bei `create`) über
`updateFields.note`: Der native Node baut daraus serverseitig automatisch
ein Artikel-Objekt mit `internal: true` / `type: note` /
`content_type: text/html` — dadurch **zwingend ausschließlich eine
interne Notiz**, es wird nichts automatisch an den Kunden verschickt und
sonst passiert am Ticket nichts weiter. Im selben Update-Call setzt
`updateFields.state_id` zusätzlich den Ticket-Status auf `pending close`
(UI-Label „Warten auf Schließen“); **es werden keine Tags mehr gesetzt**
— der Statuswechsel weg von `state_id` „new“/„open“ übernimmt gleichzeitig
die Rolle des früheren Tags als Schutz vor Doppel-Entwürfen, da der
IF-Node oben nur noch Tickets mit Status „new“ oder „open“ durchlässt.
Alle drei nativen
Zammad-Nodes nutzen dasselbe, bereits in n8n hinterlegte Credential
**„Zammad ticket.emue365“** (Typ „Zammad Basic Auth API“). Zum Schluss
löst der Workflow einen ntfy-Push aus (Topic `zammad-ki-entwuerfe`, siehe
[docs/1-benachrichtigungen/10010-ntfy.md](../1-benachrichtigungen/10010-ntfy.md)),
damit jemand den Entwurf prüfen und in Zammad manuell freigeben kann.

**Wichtig:** Der letzte Node „Abschluss (immer genau 1 Item)“ läuft im
Modus „Run Once for All Items“ und wird zusätzlich direkt vom
Trigger-Node gespeist — dadurch liefert dieser Sub-Workflow **immer genau
ein Ergebnis-Item** zurück, auch an Tagen mit 0 gefundenen Tickets. Nur so
läuft Workflow A zuverlässig bis zum Herunterskalieren durch, statt bei
0 Tickets einfach steckenzubleiben. Die dabei gemeldete Zahl
`verarbeiteteTickets` zieht von der Item-Anzahl bewusst 1 ab
(`$input.all().length - 1`), weil genau diese eine garantierte
Passthrough-Item sonst mitgezählt würde — ungefixt hätte der Node an
Tagen mit 0 echten Tickets fälschlich „1 verarbeitet“ gemeldet (gefunden
beim ersten echten Testlauf, 27.08.2026).

Rein regelbasierte Standardanfragen sollten **nicht** über diesen
Workflow laufen, sondern direkt über Zammads eigene Trigger/Text-Module
in der externen Instanz — einfacher und ohne LLM-Kosten.

> **Hinweis zur Zuverlässigkeit:** Resource/Operation/Feldnamen der drei
> nativen Zammad-Nodes sind anhand des n8n-Zammad-Node-Quelltexts
> (`n8n-io/n8n`, `packages/nodes-base/nodes/Zammad`) verifiziert, aber die
> konkreten IDs (`state_id`, `owner_id`, `group_id` — instanzabhängig)
> **nicht gegen die laufende externe Zammad-Instanz getestet**. Nach dem
> Import jeden dieser Nodes einmal öffnen, die CHANGE-ME-Platzhalter durch
> echte Werte ersetzen (idealerweise per Dropdown, nicht als Text
> eintippen) und prüfen, ob Felder wie erwartet angezeigt werden.

**NACH DEM IMPORT zwingend nötig** (Details auch in der `meta.description`
der beiden Workflow-JSONs):
1. **Beide Workflows importieren**, Sub-Workflow B zuerst. In Workflow A,
   Node „Zammad Tickets verarbeiten“ (Execute Workflow), die echte
   Workflow-ID von B eintragen — wird beim Import nicht automatisch
   verknüpft.
2. Credential **„carplay-api API Token“** (Header-Auth, `Authorization:
   Bearer <TOKEN>` — der bereits versiegelte `apiToken` aus
   `argocd/apps/tech/carplay-api/values.yaml`, siehe
   [300d0-carplay-api.md](300d0-carplay-api.md)) anlegen und dem Node
   „Worker-0 wecken“ in Workflow A zuweisen.
3. In den **drei nativen Zammad-Nodes** in Workflow B das bestehende
   Credential **„Zammad ticket.emue365“** (Typ Zammad Basic Auth API) neu
   zuweisen — Credential-IDs werden beim Import nicht übernommen.
4. Im IF-Node „Nur relevante Tickets“ (Workflow B) alle drei
   CHANGE-ME-Platzhalter setzen: `state_id` für Status „new“ (Standard-
   Zammad-Installation: `1`), `owner_id` des KI-Agenten (nur dessen
   zugewiesene Tickets werden bearbeitet), optional `group_id`-Ausschluss
   (Bedingung sonst entfernen).
5. `state_id` (Zielwert für Status „pending close“, Standard-Zammad-
   Installation: `4`) im Node „Entwurf als interne Notiz speichern +
   Status setzen“ (Workflow B) setzen.
6. Topic `zammad-ki-entwuerfe` in der ntfy-App abonnieren.
7. Ollama muss vorher einmal eingerichtet sein (Modell gezogen, RBAC
   deployt) — siehe [300g0-ollama.md](300g0-ollama.md).
8. **Beide Workflows aktivieren** — Import allein reicht nicht.

Vor dem produktiven Einsatz: Workflow A einmal manuell auslösen (nicht auf
den täglichen Trigger warten), mit einem Test-Ticket in der externen
Zammad-Instanz — Wait-Dauer ggf. nach dem ersten echten Kaltstart-Lauf
nachjustieren.

## Beispiel-Workflow: E-Mail von Absender → WhatsApp-Kanal

Fertiger, importierbarer Workflow unter
`argocd/apps/tech/n8n/workflows/email-to-whatsapp-kanal.json`: Trifft eine
Mail von einer bestimmten Adresse ein, landet eine Nachricht (Betreff +
Textauszug, Bilder/Videos als Anhang) in einem WhatsApp-Kanal. Gepostet wird
**ausschließlich in diesen einen Kanal — Chats und Gruppen sind gesperrt:**
`TARGET_ID` muss `<Ziffern>@newsletter` sein, sonst bricht der Workflow ab
(geprüft im Code-Node und noch einmal im Sendeprozess). Das Ziel steht fest im
Workflow und kommt nie aus den Mail-Daten.

```
Postfach (IMAP, IDLE) ── FROM-Filter ──► Nachricht bauen ──► An WhatsApp senden
   E-Mail von Absender                   (Absender nochmal      (Chromium +
   (Mail danach "gelesen")                prüfen, Betreff        eigener Node-Prozess:
                                          dekodieren, Text)      whatsapp-web.js,
                                                                 Session auf PVC)
                                                │                      │
                                                └── bei Fehler ────────┴──► ntfy "whatsapp-relay"
```

> **Inoffizieller Weg, Sperrrisiko akzeptiert.** Der Versand läuft über
> WhatsApp Web (Bibliothek [whatsapp-web.js](https://github.com/wwebjs/whatsapp-web.js)),
> nicht über die offizielle Cloud-API — die kann keine Kanäle befüllen.
> WhatsApp verbietet automatisierte Nutzung; das Konto kann gesperrt werden.
> Bewusst in Kauf genommen (Business-Konto).
>
> **Kanal-Beiträge sind für alle Follower sichtbar.** Der Text enthält
> standardmäßig die ersten 500 Zeichen der Mail. `MAX_BODY_CHARS = 0` im Node
> „Nachricht bauen“ schickt nur den Betreff.

### Warum ein neues Paket im Image

Das Image enthielt zuvor `wwebjs@1.23.1-alpha.7`: eine Alpha von 04/2024 mit
Puppeteer 18, ohne Kanal-Unterstützung (kein `Channel`, keine
`@newsletter`-IDs) und von einem anderen npm-Account veröffentlicht als das
offizielle Paket. Ersetzt durch **`whatsapp-web.js@1.34.7`** (Puppeteer 24,
`Channel`-Klasse, Senden per `client.sendMessage('<id>@newsletter', …)`).

### Warum ein eigener Prozess statt `require()` im Code-Node

Der n8n-Task-Runner (führt Code-Nodes aus) friert im Prozess alle globalen
Funktionen und ihre Prototypen ein (`freezeGlobals()` in `@n8n/task-runner`),
darunter `Error.prototype`. Puppeteer — von whatsapp-web.js für die
Chromium-Steuerung genutzt — setzt bei seinen Fehlerklassen `this.name = …` und
scheitert dann mit `Cannot assign to read only property 'name' of object
'Error'`. Der eigentliche Fehler ist dabei verdeckt. Nachgestellt mit der echten
Bibliothek: ohne Härtung lädt WhatsApp Web, mit Härtung bricht schon
Puppeteers rxjs beim Laden ab.

Deshalb startet der Node „An WhatsApp senden“ pro Ausführung einen **normalen
Node.js-Prozess** (`child_process.spawn`, Funktion `waChild` im Node, per stdin
mit den Beiträgen gefüttert, Ergebnis als JSON auf stdout). Der Prozess
startet Chromium, sendet, beendet alles und hat eine eigene Zeitüberwachung.
Nötig ist nur `NODE_FUNCTION_ALLOW_BUILTIN=child_process`; ein Code-Node lädt
whatsapp-web.js selbst nicht mehr. Das gibt Code-Nodes Shell-Zugriff — der
Execute-Command-Node ist wegen `NODES_EXCLUDE: "[]"` ohnehin aktiv, die
Angriffsfläche wächst also nicht.

### Einrichtung

1. **Image + Konfiguration ausrollen:** Änderung an `image/Dockerfile` und
   `values.yaml` mergen → [Build-Workflow](../f-cicd-automatisierung/f0060-build-images.md)
   baut das Image, der Bump-PR setzt `image.tag`; nach dessen Merge startet der
   n8n-Pod neu. Reine `values.yaml`-Änderungen (Env) starten den Pod ebenfalls
   neu. Ohne `child_process` scheitert der Sende-Node mit
   `Module 'child_process' is disallowed`, ohne neues Image meldet der
   Sendeprozess `Cannot find module 'whatsapp-web.js'`.
2. **Workflow importieren** (n8n → Workflows → Import from File). Er kommt
   bewusst **inaktiv** herein.
3. **WhatsApp koppeln und Kanal-ID ermitteln** (einmalig, vom Rechner mit
   `kubectl`-Zugriff auf den TECH-Cluster):

   ```bash
   kubectl -n n8n exec -i deploy/n8n -- node - < argocd/apps/tech/n8n/scripts/whatsapp-pair.js
   ```

   Im Terminal erscheint ein QR-Code → am Handy in der WhatsApp-Business-App
   *Einstellungen → Verknüpfte Geräte → Gerät hinzufügen* scannen. Danach listet
   das Skript alle Kanäle (`…@newsletter`, mit Rolle: `owner`/`admin` dürfen
   posten) mit ID. Die Kanalliste füllt sich erst einige
   Sekunden nach dem Start, das Skript wartet dafür bis zu 45 s. Taucht ein
   Kanal trotzdem nicht auf, per Einladungslink auflösen (in der App: Kanal →
   Info → Link teilen; der Code steht hinter `whatsapp.com/channel/`):
   `kubectl -n n8n exec -i deploy/n8n -- node - --invite=<Code> < …/whatsapp-pair.js`.
   Die Session liegt danach unter `/home/node/.n8n/whatsapp-session` auf dem
   n8n-PVC und übersteht Pod-Neustarts.
4. **Platzhalter im Workflow setzen:**
   - Node „E-Mail von Absender“: IMAP-Credential zuweisen, in *Options → Custom
     Email Rules* die Adresse in `["UNSEEN", ["FROM", "…"]]` eintragen.
   - Node „Nachricht bauen“: `SENDER` — dieselbe Adresse (oder `@firma.de` für
     eine ganze Domain). Beides ist Absicht: der Trigger filtert serverseitig,
     der Code-Node prüft ein zweites Mal, bevor etwas in den Kanal geht.
   - Node „An WhatsApp senden“: `TARGET_ID` (Kanal-ID aus Schritt 3, endet auf
     `@newsletter`).
5. **ntfy-Topic `whatsapp-relay` abonnieren** ([ntfy](../1-benachrichtigungen/10010-ntfy.md)) —
   dorthin geht der Rückfall bei Fehlern.
6. **Testen, bevor aktiviert wird:** im Node „Nachricht bauen“ per *Pin Data*
   ein Test-Item mit `from`, `subject`, `textPlain` setzen und den Workflow
   manuell ausführen → die Nachricht muss im Kanal erscheinen. Danach
   **Workflow aktivieren** (Import allein reicht nicht) und eine echte
   Test-Mail vom Absender schicken.

### Verhalten und Grenzen

- **Die Mail wird als gelesen markiert**, sobald der Trigger sie abgeholt hat
  (so wird sie nicht doppelt verarbeitet). Schlägt der Versand fehl, ist sie
  trotzdem „gelesen“ — deshalb schickt der Fehlerzweig den geplanten Text per
  ntfy. Der Trigger merkt sich die zuletzt verarbeitete Mail; nach der
  Aktivierung werden ungelesene Mails des Absenders ab dem Aktivierungstag
  nachgeholt, ältere bleiben unberührt.
- **Rechne mit ca. 20–60 s Latenz** pro Mail plus Upload-Zeit je Anhang (Schätzwert, im Betrieb messen):
  Jede Ausführung startet Chromium, lädt WhatsApp Web, sendet und beendet
  alles wieder. Trifft eine zweite Mail währenddessen
  ein, wartet sie per Lock-Verzeichnis (`whatsapp-session.lock`) bis zu 2 min
  auf die erste; zwischen mehreren Nachrichten einer Ausführung liegen 4 s.
- **Anhänge** werden als eigene Beiträge direkt nach dem Text gesendet (der
  Trigger lädt sie herunter, „Nachricht bauen“ reicht sie durch). Was WhatsApp
  zulässt: **Bilder (JPEG, PNG, GIF, WebP) und MP4-Videos**. Dokumente wie
  PDF/Office/ZIP nimmt whatsapp-web.js für Kanäle nicht an.

  Was nicht übertragen wird, steht namentlich im Text: `📎 Nicht übertragen:
  bericht.pdf (Dateityp im Kanal nicht möglich)`. Grenzen: 15 MB je Anhang, 3
  Anhänge je Mail. Es werden nur echte Anhänge geladen, in den Text eingebettete
  Bilder (z. B. Signatur-Logos) nicht. Komplett ignorieren:
  `SEND_ATTACHMENTS = false` im Node „Nachricht bauen“ und im Trigger *Download
  Attachments* ausschalten. Im Binary-Modus `filesystem` holt der Runner den
  Inhalt über `helpers.getBinaryDataBuffer` nach, im Modus `default` steckt er
  direkt im Item — beides ist berücksichtigt.
- **Umlaute:** Der IMAP-Trigger dekodiert Quoted-Printable-Text nur bei exakt
  `charset=UTF-8` richtig; sonst kommen UTF-8-Bytes als Latin-1-Zeichen an
  („Grüßen“ → „GrÃ¼Ãen“). „Nachricht bauen“ macht das rückgängig, wenn die
  Bytes gültiges UTF-8 ergeben; echter Latin-1-Text bleibt unverändert.
- **Absender nicht kryptographisch geprüft:** Der Filter vertraut dem
  `From`-Header. Ein gefälschter Absender kommt durch, wenn der Mailserver
  ihn nicht schon vorher aussortiert (SPF/DKIM/DMARC dort prüfen).
- **Chromium-Profil liegt auf dem NFS-PVC** (`nas`, wie die n8n-SQLite). Das
  funktioniert, ist aber langsamer und bei Lock-Problemen die erste Verdächtige;
  ggf. für die Session ein eigenes `local-path`-Volume einhängen.

### Fehlerbehebung

| Symptom | Ursache / Lösung |
|---|---|
| `Module 'child_process' is disallowed` | `NODE_FUNCTION_ALLOW_BUILTIN=child_process` noch nicht ausgerollt. Prüfen: `kubectl -n n8n exec deploy/n8n -- env \| grep NODE_FUNCTION` |
| `WhatsApp-Prozess endete mit Code 1: … Cannot find module 'whatsapp-web.js'` | Neues Image noch nicht ausgerollt. Prüfen: `kubectl -n n8n exec deploy/n8n -- ls /opt/wwebjs/node_modules/whatsapp-web.js` |
| `TARGET_ID muss ein WhatsApp-Kanal sein …` | Absichtliche Sperre: nur `<Ziffern>@newsletter` wird akzeptiert, keine Gruppen/Chats |
| `Cannot assign to read only property 'name' of object 'Error'` | Puppeteer läuft im Runner statt im eigenen Prozess (alte Workflow-Version ohne `waChild`). Aktuelle JSON importieren |
| `WhatsApp-Session nicht (mehr) gekoppelt (QR-Code angefordert)` | Session fehlt oder wurde ungültig (z. B. Gerät in der App entfernt, Handy lange offline). `whatsapp-pair.js` erneut ausführen |
| `Ein anderer WhatsApp-Versand läuft noch (Lock …)` | Lock von einem hart beendeten Lauf, wird nach ~5 min automatisch übernommen. Sofort: `kubectl -n n8n exec deploy/n8n -- rmdir /home/node/.n8n/whatsapp-session.lock` |
| `WhatsApp Web wurde nicht rechtzeitig bereit` | Chromium zu langsam/OOM (Pod-Limit 2 Gi): `kubectl -n n8n top pod`, `kubectl -n n8n describe pod` auf `OOMKilled` prüfen; NFS-Latenz; ggf. `READY_TIMEOUT_MS` erhöhen |
| Senden schlägt fehl, obwohl gekoppelt | Konto ist im Kanal nicht Inhaber/Admin → in der Ausgabe von `whatsapp-pair.js` muss bei der Rolle `owner` oder `admin` stehen |
| Nichts passiert bei neuen Mails | Workflow aktiv? Execution-Liste ansehen. Wird die Mail vom Filter gefunden (Adresse exakt wie im `From`, IMAP-Suche ist ein Teilstring-Vergleich)? Bei „Trigger lieferte N Mail(s), aber keine passt zu SENDER“ stimmen Trigger-Filter und `SENDER` nicht überein |

## Custom Image (n8n-nodes-imap, whatsapp-web.js)

`argocd/apps/tech/n8n/image/Dockerfile` baut ein eigenes Image auf
Basis des offiziellen `n8nio/n8n`-Images mit `n8n-nodes-imap` vorinstalliert
(braucht sonst manuelle Installation über die UI, die bei jedem Pod-Neustart
verloren ginge, da `~/.n8n` zwar persistent ist, `N8N_CUSTOM_EXTENSIONS`
aber bewusst außerhalb davon liegt — Details im Dockerfile-Kommentar).
Zusätzlich sind `whatsapp-web.js` + `qrcode` und ein Chromium unter
`/opt/wwebjs` bzw. `/usr/bin/chromium-browser` enthalten (siehe
[E-Mail → WhatsApp-Kanal](#beispiel-workflow-e-mail-von-absender--whatsapp-kanal)).
Gebaut/gepusht wird automatisiert über `.github/workflows/build-images.yml`
(siehe [Chart-README dort](../../argocd/apps/tech/pacman/README.md#image-bauen)
fürs allgemeine Vorgehen, [f0060-build-images.md](../f-cicd-automatisierung/f0060-build-images.md)
für Details): jeder Push nach `main`, der `image/Dockerfile` ändert, löst
automatisch einen Build+Push nach `ghcr.io/pkr-lab/n8n-custom` aus — kein
manuelles `argo submit` mehr nötig.

Bei einem n8n-Versions-Update: `FROM n8nio/n8n:<version>` im Dockerfile
anpassen und committen/pushen — das baut automatisch. Den im Job-Summary
des Workflow-Runs gemeldeten Tag (`sha-<commit-sha>`) danach manuell in
`image.tag` in `values.yaml` eintragen und committen. `n8n-nodes-imap`-
Version im Dockerfile (`npm install n8n-nodes-imap@<version>`) unabhängig
davon aktuell halten, siehe [npm-Registry](https://www.npmjs.com/package/n8n-nodes-imap).

## Konfiguration (values.yaml)

| Key | Bedeutung | Default |
|---|---|---|
| `env.N8N_HOST` | Hostname für interne Links und Webhooks | `n8n.prod.homeserver` |
| `env.WEBHOOK_URL` | Basis-URL für Webhook-Endpunkte | `http://n8n.prod.homeserver/` |
| `env.N8N_BASIC_AUTH_ACTIVE` | HTTP Basic Auth aktivieren | `false` |
| `persistence.size` | Datenspeicher (Workflows + SQLite) | `5Gi` |
| `env.NODE_FUNCTION_ALLOW_BUILTIN` | Node.js-Builtins für Code-Nodes (WhatsApp-Sendeprozess) | `child_process` |
| `xibosignage.enabled` | xibosignage-Inbox/Display-NFS-Mounts aktivieren | `true` |

n8n hat ohne weitere Absicherung keinen Login-Schutz auf dem Netzwerk.

setzen (bereits so konfiguriert, siehe `values.yaml`).
