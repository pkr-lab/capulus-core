# n8n — Low-Code-Automatisierung

n8n ist ein selbst gehosteter Workflow-Automatisierer (Open-Source-Alternative
zu Zapier/Make). Über eine visuelle Oberfläche lassen sich Dienste verknüpfen,
z. B.:

- Neues Dokument in Paperless → ntfy-Push
- Neuer GitHub-Release → Zammad-Ticket
- Wetterwarnung DWD → ntfy-Alert
- Neues Ticket in externem Zammad → KI-Antwortentwurf (täglich, lokales LLM)

---

## Architektur

```
n8n.prod.homeserver  →  Traefik  →  n8n (Port 5678)
                                   └── PVC: data (5 Gi, nas)
```

- **Datenbank:** SQLite (in `/home/node/.n8n`)
- **Webhooks:** erreichbar unter `http://n8n.prod.homeserver/webhook/...`

---

## Erster Start

n8n ist nach dem Deploy unter **http://n8n.prod.homeserver** erreichbar. Beim
ersten Öffnen wird ein Owner-Account angelegt.

---

## Beispiel-Workflow: Paperless → ntfy

```
Trigger: Paperless Webhook (POST /webhook/paperless)
  → HTTP Request: GET paperless.homeserver/api/documents/{id}/
  → ntfy Node: Push "📄 Neues Dokument: {title}"
```

1. In n8n: *Neuer Workflow* → Trigger: **Webhook**
2. Webhook-URL aus n8n kopieren
3. In Paperless: *Einstellungen* → *Workflow-Trigger* → URL eintragen
4. ntfy-Node hinzufügen, Topic und Server konfigurieren

## Beispiel-Workflow: xibosignage Inbox → Display

Fertiger, importierbarer Workflow unter
`argocd/apps/workloads/n8n/workflows/xibosignage-inbox-to-display.json`: beobachtet
einen NFS-gemounteten Ordner (`/data/xibosignage-inbox`) per **Local File
Trigger**, skaliert neue Bilder auf eine Pi-taugliche Auflösung (**Edit
Image**) und schreibt sie nach `/data/xibosignage-display`, von wo ein
Raspberry-Pi-Kiosk sie per Slideshow anzeigt. Die beiden Ordner werden dafür
per statischer NFS-PV/PVC in den n8n-Pod gemountet
(`values.yaml` → `xibosignage`). Vollständige Anleitung inkl. NAS-Ordner-
Setup und Pi-Rollout: **[docs/3-apps-workloads/300e0-xibosignage.md](300e0-xibosignage.md)**.

## Beispiel-Workflow: Jährliche Secrets-Rotation → Zammad-Ticket

Fertiger, importierbarer Workflow unter
`argocd/apps/workloads/n8n/workflows/yearly-secrets-rotation-reminder.json`:
**Schedule Trigger** (jährlich, Default 15. Januar 08:00 Uhr) → nativer
**Zammad-Node** (Ticket → Create) eröffnet ein Ticket in der Gruppe
`Support::Administration` als Erinnerung, die zentralen Secrets zu prüfen/
rotieren. Nutzt den echten `n8n-nodes-base.zammad`-Node (Credential-Typ
„Zammad Token Auth API“), nicht den generischen HTTP-Request-Node wie beim
`banana-pi-down-to-zammad.json`-Workflow. Vollständige Anleitung inkl.
Rotations-Checkliste je Secret: **[docs/d-sicherheit/d0060-secrets-rotation.md](../d-sicherheit/d0060-secrets-rotation.md)**.

## Beispiel-Workflow: Nightly Worker Update → Zammad-Ticket

Fertiger, importierbarer Workflow unter
`argocd/apps/workloads/n8n/workflows/nightly-worker-update-to-zammad.json`:
**Webhook** (POST `/webhook/nightly-worker-update`) → **Code**-Node baut aus
dem JSON-Bericht Titel + lesbaren Text (Status je Worker, geänderte Pakete,
Ansible-PLAY-RECAP, automatischer Reboot) → nativer **Zammad-Node** (Ticket →
Create) eröffnet ein Ticket in der Gruppe `Support::Administration`.
Absender ist `nightly-worker-wake.sh` (läuft nachts um 01:00 Uhr auf dem
Homeserver, siehe [docs/2-betrieb-hardware/20030-nightly-worker-update.md](../2-betrieb-hardware/20030-nightly-worker-update.md))
— IMMER am Ende jedes Laufs, egal ob erfolgreich, teilweise fehlgeschlagen
oder komplett abgebrochen. Nutzt denselben `n8n-nodes-base.zammad`-Node wie
`yearly-secrets-rotation-reminder.json`.

## Beispiel-Workflow: Externer Zammad → KI-Antwortentwurf (Ollama)

Zwei zusammengehörige, importierbare Workflows unter
`argocd/apps/workloads/n8n/workflows/` — aufgeteilt, damit die
Lebenszyklus-Steuerung des lokalen LLM (Start/Stop) sauber von der
eigentlichen Ticket-Verarbeitung getrennt ist:

### A) `zammad-externer-ki-lauf-taeglich.json` (Haupt-Workflow)

**Schedule Trigger** (**1× täglich**, Default 07:00 Uhr) orchestriert den
kompletten Lebenszyklus des lokalen LLM
([Ollama](300g0-ollama.md), läuft mit `replicas: 0` im Ruhezustand — kein
Dauerbetrieb):
1. **Worker-0 wecken** — `POST carplay-api.homeserver/api/power/wake`
   (`{"target": "worker-0"}`), da der bestehende `cluster_power_manager`
   nur reaktiv auf Last reagiert, nicht auf diesen konkreten Bedarf.
2. **Ollama hochskalieren** — direkter Kubernetes-API-Call (PATCH auf die
   Scale-Subresource) auf `replicas: 1`, authentifiziert mit dem
   automatisch gemounteten ServiceAccount-Token des n8n-Pods selbst (RBAC
   dafür in `argocd/apps/workloads/ollama/templates/role-n8n-scaler.yaml`
   — n8n darf NUR dieses eine Deployment skalieren).
3. **Wait** (Startwert 150s) für Node-Boot + Pod-Start + Ollama-Bereitschaft.
4. **Execute Workflow** ruft Sub-Workflow B auf und wartet auf dessen
   Abschluss.
5. **Ollama herunterskalieren** — dieselbe PATCH-Logik, zurück auf
   `replicas: 0`. Läuft garantiert, auch wenn Sub-Workflow B an dem Tag 0
   Tickets gefunden hat (siehe unten).

Details zum Scale-to-Zero-Pattern, RBAC und ArgoCD-`ignoreDifferences`:
**[300g0-ollama.md](300g0-ollama.md)**.

### B) `zammad-tickets-verarbeiten.json` (Sub-Workflow)

Kein eigener Zeitplan — startet ausschließlich per **Execute Workflow
Trigger**, aufgerufen von Workflow A, während Ollama bereits läuft. Sucht
per **nativem `n8n-nodes-base.zammad`-Node** (Ticket → Get Many) neue
Tickets in der **externen** Zammad-Instanz `https://ticket.emue365.de`
(anderer Account als `zammad.homeserver`), lädt je Ticket den
Artikel-Verlauf ebenfalls nativ (Ticket Article → Get Many), schickt ihn
per HTTP-Request an das lokale Ollama
(`http://ollama.ollama.svc.cluster.local:11434/api/generate`, Modell
`llama3.1:8b`, kein Auth nötig) und speichert den Antwortvorschlag wieder
nativ (Ticket → Update + Article) als **interne Notiz** — es wird
**nichts automatisch an den Kunden verschickt**. Alle drei nativen
Zammad-Nodes nutzen dasselbe, bereits in n8n hinterlegte Credential
**„Zammad ticket.emue365“** (Typ „Zammad Basic Auth API“). Ein Tag
(`ki-entwurf-erstellt`) verhindert Doppel-Entwürfe; da der native Node
keine Tag-Ressource anbietet, bleibt dieser eine Schritt ein roher
HTTP-Request-Node (braucht zusätzlich ein generisches „Basic
Auth“-Credential mit denselben Zugangsdaten). Zum Schluss löst der
Workflow einen ntfy-Push aus (Topic `zammad-ki-entwuerfe`, siehe
[docs/1-benachrichtigungen/10010-ntfy.md](../1-benachrichtigungen/10010-ntfy.md)),
damit jemand den Entwurf prüfen und in Zammad manuell freigeben kann.

**Wichtig:** Der letzte Node „Abschluss (immer genau 1 Item)“ läuft im
Modus „Run Once for All Items“ und wird zusätzlich direkt vom
Trigger-Node gespeist — dadurch liefert dieser Sub-Workflow **immer genau
ein Ergebnis-Item** zurück, auch an Tagen mit 0 gefundenen Tickets. Nur so
läuft Workflow A zuverlässig bis zum Herunterskalieren durch, statt bei
0 Tickets einfach steckenzubleiben.

Rein regelbasierte Standardanfragen sollten **nicht** über diesen
Workflow laufen, sondern direkt über Zammads eigene Trigger/Text-Module
in der externen Instanz — einfacher und ohne LLM-Kosten.

> **Hinweis zur Zuverlässigkeit:** Die Parameter der drei nativen
> Zammad-Nodes sowie des Execute-Workflow-Node-Typs sind anhand der
> einzigen im Repo bereits bestätigten Zammad-Node-Struktur (`ticket`/
> `create` in `yearly-secrets-rotation-reminder.json`) abgeleitet, aber
> **nicht gegen eine laufende n8n-Instanz getestet**. Nach dem Import
> jeden dieser Nodes einmal öffnen und prüfen, ob Resource/Operation/
> Felder wie erwartet angezeigt werden.

**NACH DEM IMPORT zwingend nötig** (Details auch in der `meta.description`
der beiden Workflow-JSONs):
1. **Beide Workflows importieren**, Sub-Workflow B zuerst. In Workflow A,
   Node „Zammad Tickets verarbeiten“ (Execute Workflow), die echte
   Workflow-ID von B eintragen — wird beim Import nicht automatisch
   verknüpft.
2. Credential **„carplay-api API Token“** (Header-Auth, `Authorization:
   Bearer <TOKEN>` — der bereits versiegelte `apiToken` aus
   `argocd/apps/workloads/carplay-api/values.yaml`, siehe
   [300d0-carplay-api.md](300d0-carplay-api.md)) anlegen und dem Node
   „Worker-0 wecken“ in Workflow A zuweisen.
3. In den **drei nativen Zammad-Nodes** in Workflow B das bestehende
   Credential **„Zammad ticket.emue365“** (Typ Zammad Basic Auth API) neu
   zuweisen — Credential-IDs werden beim Import nicht übernommen.
4. Für den Node „Ticket taggen“ in Workflow B zusätzlich ein
   **generisches „Basic Auth“-Credential** mit denselben Zugangsdaten
   anlegen und zuweisen.
5. Gruppen-Filter im IF-Node „Nur relevante Tickets“ (Workflow B) setzen.
6. Topic `zammad-ki-entwuerfe` in der ntfy-App abonnieren.
7. Ollama muss vorher einmal eingerichtet sein (Modell gezogen, RBAC
   deployt) — siehe [300g0-ollama.md](300g0-ollama.md).
8. **Beide Workflows aktivieren** — Import allein reicht nicht.

Vor dem produktiven Einsatz: Workflow A einmal manuell auslösen (nicht auf
den täglichen Trigger warten), mit einem Test-Ticket in der externen
Zammad-Instanz — Wait-Dauer ggf. nach dem ersten echten Kaltstart-Lauf
nachjustieren.

## Custom Image (n8n-nodes-imap)

`argocd/apps/workloads/n8n/image/Dockerfile` baut ein eigenes Image auf
Basis des offiziellen `n8nio/n8n`-Images mit `n8n-nodes-imap` vorinstalliert
(braucht sonst manuelle Installation über die UI, die bei jedem Pod-Neustart
verloren ginge, da `~/.n8n` zwar persistent ist, `N8N_CUSTOM_EXTENSIONS`
aber bewusst außerhalb davon liegt — Details im Dockerfile-Kommentar).
Gebaut/gepusht wird analog zu `pacman` über das `kaniko-build-push`
Argo-WorkflowTemplate (siehe [Chart-README dort](../../argocd/apps/workloads/pacman/README.md#image-bauen)
fürs allgemeine Vorgehen):

```bash
argo submit -n argo-workflows --from workflowtemplate/kaniko-build-push \
  -p repo=https://github.com/pkr-lab/capulus-core.git \
  -p revision=main \
  -p context=argocd/apps/workloads/n8n \
  -p dockerfile=image/Dockerfile \
  -p image=ghcr.io/pkr-lab/n8n-custom:<n8n-version>-imap
```

**Wichtig:** `kaniko-build-push` baut immer vom **gepushten** Stand des
angegebenen `revision` (Standard `main`) — lokale, noch nicht committete
Änderungen am Dockerfile werden nicht berücksichtigt. Erst committen und
pushen, dann bauen, sonst landet unter dem neuen Tag versehentlich noch der
alte Image-Inhalt in der Registry.

Bei einem n8n-Versions-Update: `FROM n8nio/n8n:<version>` im Dockerfile
sowie `image.tag` in `values.yaml` gemeinsam anpassen, dann wie oben neu
bauen. `n8n-nodes-imap`-Version im Dockerfile (`npm install
n8n-nodes-imap@<version>`) unabhängig davon aktuell halten, siehe
[npm-Registry](https://www.npmjs.com/package/n8n-nodes-imap).

## Konfiguration (values.yaml)

| Key | Bedeutung | Default |
|---|---|---|
| `env.N8N_HOST` | Hostname für interne Links und Webhooks | `n8n.prod.homeserver` |
| `env.WEBHOOK_URL` | Basis-URL für Webhook-Endpunkte | `http://n8n.prod.homeserver/` |
| `env.N8N_BASIC_AUTH_ACTIVE` | HTTP Basic Auth aktivieren | `false` |
| `persistence.size` | Datenspeicher (Workflows + SQLite) | `5Gi` |
| `xibosignage.enabled` | xibosignage-Inbox/Display-NFS-Mounts aktivieren | `true` |

## Sicherheitshinweis

n8n hat ohne weitere Absicherung keinen Login-Schutz auf dem Netzwerk.
Empfohlen für den Home-Lab-Einsatz: `N8N_BASIC_AUTH_ACTIVE=true` + Credentials
setzen (bereits so konfiguriert, siehe `values.yaml`).
